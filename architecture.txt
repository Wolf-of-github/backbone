  - security
    - Baseline application security guidelines (enforced in code review + CI)
      - Injection: no shell string interpolation
        - Use execFile/spawn with arg arrays, not exec() / child_process.exec
        - Python: subprocess.run([...]) without shell=True, never os.system()
        - Parameterized DB queries only, never string-built MongoDB queries
      - Code execution: no eval(), no new Function() on dynamic strings
      - XSS: no raw innerHTML / outerHTML / insertAdjacentHTML / document.write
        - React: avoid dangerouslySetInnerHTML; sanitize with DOMPurify if unavoidable
        - Escape/encode all user content on output; set a strict Content-Security-Policy
      - Unsafe deserialization: no pickle/marshal/yaml.load on untrusted input
        - Use JSON or schema-validated parsers (pydantic, zod); yaml.safe_load only
      - XXE: use a hardened XML parser (defusedxml), external entities disabled
      - Secrets: never hardcode keys/passwords/tokens; load from k3s secrets
        - Secret scanning in CI to block commits containing credentials
      - Crypto: AES-GCM (or AES-CBC + HMAC), never ECB; use createCipheriv with IV
        - Bcrypt/argon2 for passwords; never MD5/SHA1 for auth
      - TLS: never disable certificate verification (no rejectUnauthorized:false,
        verify=False, InsecureSkipVerify)
      - Access control: authenticate every request at the gateway; enforce object-level
        authorization in services (prevent IDOR); deny by default
      - SSRF: validate/allowlist outbound URLs from user input; block internal IP ranges
      - Path traversal: normalize paths, confine to an allowed base directory
      - CI/CD: no untrusted input in shell steps or checkout refs; pin action versions
      - Dependencies: lockfiles, npm audit / CVE scan in pipeline, patch critical/high
      - Enforcement: security-guidance plugin (edit-time pattern warnings, LLM diff
        review, agentic commit review) gates every change before merge
  - horizontal-scale
    - The point of backbone: add machines, get capacity - no per-service rewiring. Linux only.
    - Shape: a real k3s SERVER (control plane, embedded etcd) on one Linux host; every other machine
      (EC2, spare box, another cloud) joins as a k3s AGENT with `scripts/node-join.sh`.
      Any laptop drives the cluster by pointing kubectl at ./kubeconfig - nothing installed on the laptop.
    - Why not "k3s in Docker" (k3d/kind) as the default: those run on one Docker daemon = one machine.
      They give orchestration within that machine's RAM/CPU ceiling, never additional hardware. Offloading
      heavy work needs another machine's kernel, which means real k3s on each. (k3d stays useful only as a
      throwaway local dev cluster - not part of Phase 0.)
    - A joined machine installs ONLY the k3s agent (~100 MB, its own containerd). No Docker, no kubectl.
      One command: `curl ... | K3S_URL=https://<server>:6443 K3S_TOKEN=<tok> sh -` (node-join.sh wraps it).
    - Location transparency: a pod on the EC2 node and a pod on the main box talk via the same
      `svc.namespace.svc.cluster.local` DNS. The flannel overlay carries pod-to-pod across machines.
      You never wire IPs between services.
    - Scaling a service = raise `replicas` / HPA `maxReplicas`; the scheduler spreads pods across all
      nodes. Out of room -> join another machine. No reconfiguration.
    - Node-to-node networking (the one real cost). Open BETWEEN nodes only
      (e.g. one AWS security group referencing itself):
        6443/tcp   Kubernetes API      (agents -> server)
        10250/tcp  kubelet             (all <-> all)
        51820/udp  flannel WireGuard   (all <-> all)   [WIREGUARD=true, default]
        8472/udp   flannel VXLAN       (all <-> all)   [WIREGUARD=false, trusted network only]
      Cross-network (home/office <-> AWS VPC): WIREGUARD=true (encrypts the overlay) + NODE_EXTERNAL_IP
      set to each node's routable IP. Same-VPC: plain VXLAN is fine.

    - FIREWALL / SECURITY-GROUP REQUIREMENTS (authoritative list - Terraform, cloud-init, and any
      hand-provisioned node must match this exactly):

        proto/port   direction                  needed for                       when
        ----------   ------------------------   ------------------------------    -------------------
        6443/tcp     agents  -> server          Kubernetes API / node join       always (multi-node)
        10250/tcp    all    <-> all             kubelet (logs, exec, metrics)    always (multi-node)
        51820/udp    all    <-> all             flannel WireGuard overlay        WIREGUARD=true (default)
        8472/udp     all    <-> all             flannel VXLAN overlay            WIREGUARD=false
        2379-2380/tcp servers <-> servers       embedded-etcd peer/client        Phase 6 HA (>1 server) only

      - EXACTLY ONE overlay port is required: 51820/udp (WireGuard) OR 8472/udp (VXLAN), matching
        WIREGUARD. Opening both is harmless; opening neither = cross-node pod traffic and in-cluster
        DNS silently time out (no error, 100% packet loss). This is the single most common bring-up
        failure.
      - Source scoping: in one cloud, use a security group that references itself. Cross-network,
        scope the overlay + kubelet ports to the other nodes' routable IPs (or the tailnet CIDR
        100.64.0.0/10 when TAILSCALE=true - see below).
      - Public ingress (80/443 to Kong) is NOT in this list - it is Phase 2, on the gateway node
        only, never node-to-node.
      - Egress: nodes need outbound 443/tcp to fetch images and the k3s installer (until the Phase 5
        in-cluster registry). Terraform modules should allow egress-all unless there is a reason not to.

    - TAILSCALE=true specifics (NAT'd / no-public-IP nodes, joined over a tailnet):
      - The overlay still needs its UDP port (51820 or 8472) reachable between the nodes' TAILNET
        addresses. If Tailscale negotiates a DIRECT connection (common on cloud VMs), that UDP rides
        the nodes' PUBLIC IPs and is subject to the cloud security group - so the SG must still allow
        51820/udp (or 8472/udp), sourced from 100.64.0.0/10. Only pure DERP-relayed tailnets avoid
        this, and you should not rely on relay for the data plane.
      - Every node must pin its k3s identity + flannel to the tailnet interface, or k3s picks the
        default-route NIC (e.g. LAN wifi) and peers cannot route to it:
          --node-ip=<tailscale ip -4>   --flannel-iface=tailscale0   --node-external-ip=<same>
        cluster-up.sh and node-join.sh set all three when TAILSCALE=true; the Terraform cloud-init
        MUST do the same.
      - MTU: flannel auto-sizes its overlay MTU to ~1200 to fit inside the 1280-byte tailnet MTU.
        Do not override it upward.
    - Failure: an agent dying -> its pods reschedule onto the others. The server is still a single
      point of failure until Phase 6 (embedded-etcd HA: 3 servers).
    - External services that will NEVER run in-cluster (managed RDS, a GPU box you won't put k3s on):
      represent them as a selector-less Service + EndpointSlice, or ExternalName. Callers use a normal
      Service DNS name; the target lives outside. This is the exception, not the scaling mechanism.

  - Phase 0 - Substrate: develop from 0 -> 100 (instantiate every file, then code it, then verify)
    - Runtime decision: LINUX ONLY. `make cluster` installs a real k3s SERVER (control plane, embedded
      etcd, HA-ready) on this host; other Linux machines join as k3s AGENTS with scripts/node-join.sh.
      Any laptop drives the cluster by pointing kubectl at ./kubeconfig - nothing installed on the laptop.
      - Prereqs on the server: Linux + `curl` + `sudo` + `kubectl`.
        Prereqs on a joining worker: Linux + `curl` + `sudo` ONLY (no Docker, no kubectl).
      - `scripts/cluster-up.sh` installs k3s server with `--cluster-init`, `--disable=traefik`,
        `--flannel-backend=wireguard-native` when WIREGUARD=true, `--tls-san`/`--node-external-ip`/role
        label from .env. When TAILSCALE=true it also pins `--node-ip=<tailscale ip -4>` and
        `--flannel-iface=tailscale0` (without these k3s binds the default-route NIC - e.g. LAN wifi -
        and peers on another network cannot reach it; node-join.sh does the same on the worker).
        Caches the join token to `.secrets/cluster-join.env` (gitignored).
      - No in-cluster registry in Phase 0 - workers pull from public registries until Phase 5 stands up
        the real one (authenticated, behind Kong + TLS).
      - Why not k3d/kind ("k3s in Docker") even for a single machine: they run on one Docker daemon =
        one machine's RAM/CPU. They cannot pool other machines' hardware, which is the whole point of
        backbone. k3d remains only a throwaway local dev cluster - not part of Phase 0.
      - DROPPED from earlier drafts: k3s-config.yaml, kubeconfig.example, registry-secret.sh,
        bootstrap-registry.sh, registries.yaml(.example), k8s/platform/registry/*, config/k3d-cluster.yaml,
        and the MULTI_NODE switch. The k3s-server install is now the only path in cluster-up.sh.

      - conf-configmap.yaml: `redis.conf` -
          bind 0.0.0.0
          protected-mode no            # requirepass is the gate; cluster-internal only
          appendonly yes               # AOF on now; fsync policy tuned in Phase 6
          appendfsync everysec
          save 900 1 / save 300 10 / save 60 10000     # RDB snapshots
          maxmemory-policy noeviction  # BullMQ jobs must not be evicted
          dir /data
        (requirepass is NOT in the file - passed via `--requirepass "$(cat /secret/password)"` in the
        container command so the value never lands in a ConfigMap.)
      - statefulset.yaml: `redis` StatefulSet, `serviceName: redis`, replicas 1, image `redis:7.2-alpine`.
        Command: `redis-server /etc/redis/redis.conf --requirepass "$REDIS_PASSWORD"` with
        `REDIS_PASSWORD` from `secretKeyRef: redis-password/password`. Mounts: conf-configmap at
        /etc/redis, `volumeClaimTemplate` `data` (1Gi, RWO, default SC) at /data. Probes:
        `redis-cli -a "$REDIS_PASSWORD" ping` for liveness+readiness (`exec` probe). `securityContext`
        runAsNonRoot, fsGroup so the PVC is writable.
      - service.yaml: headless (`clusterIP: None`) Service `redis` in ns data, port 6379 -> stable DNS
        `redis.data.svc.cluster.local`.
      - Verify: `kubectl -n data rollout status statefulset/redis`; from a throwaway `redis:7.2-alpine`
        pod, `redis-cli -h redis.data.svc -a <pw> SET k v` / `GET k` / `DEL k`; PVC `data-redis-0` Bound.

    - Step 4 - MongoDB manifests (k8s/data/mongodb/*)
      - mongod-conf-configmap.yaml: `mongod.conf` -
          net: { bindIp: 0.0.0.0, port: 27017 }
          storage: { wiredTiger: { engineConfig: { cacheSizeGB: 0.25 } } }
          security: { authorization: enabled }
          # replication: { replSetName: rs0 }   # commented - Phase 6
      - init-configmap.yaml: `init-app-user.js` - run once against the fresh volume; creates
        `MONGO_APP_DB` and the least-privilege app user (`readWrite` on that DB only) from env vars
        the init step passes in. Idempotent (guarded by a `db.getUser()` check).
      - statefulset.yaml: `mongodb` StatefulSet, `serviceName: mongodb`, replicas 1, image `mongo:7.0`.
        - Env: `MONGO_INITDB_ROOT_USERNAME` / `MONGO_INITDB_ROOT_PASSWORD` from
          `secretKeyRef: mongodb-credentials/root-*` (the official image bootstraps the root user on an
          empty datadir).
        - App user + DB: an `initContainer` OR a `postStart`/one-shot Job running `mongosh` with the
          init-configmap script, taking app-* + root-* from the secret. Chosen approach: a small
          `initContainer` is race-prone against mongod start; use a one-shot `Job`
          (`k8s/data/mongodb/init-job.yaml`, added here) that runs after the StatefulSet is Ready and
          `mongosh`es the init script. bootstrap-data.sh sequences it.
        - Mounts: mongod-conf-configmap at /etc/mongo, `volumeClaimTemplate` `data` (2Gi, RWO,
          default SC) at /data/db. Command: `mongod --config /etc/mongo/mongod.conf`.
        - Probes: `mongosh --quiet --eval "db.adminCommand('ping')"` (exec) for liveness+readiness.
        - `securityContext`: runAsNonRoot (mongo uid 999), fsGroup 999.
      - service.yaml: headless Service `mongodb` in ns data, port 27017 -> `mongodb.data.svc.cluster.local`.
      - Update Step 0 stub list to include /k8s/data/mongodb/init-job.yaml.
      - Verify: `kubectl -n data rollout status statefulset/mongodb`; init Job `Completed`; from a
        throwaway `mongo:7.0` pod, `mongosh "mongodb://<app-user>:<pw>@mongodb.data.svc/<db>"` then
        `insertOne` / `findOne` / `drop`; a root-only op from the app user is denied; PVC
        `data-mongodb-0` Bound.

    - Step 5 - Orchestration (scripts/bootstrap-data.sh)
      - `set -euo pipefail`; source lib.sh; `load_env`; `need kubectl`; assert ns data + Phase 0
        default SC present.
      - Order: (1) `scripts/data-secrets.sh`; (2) apply redis conf-configmap -> statefulset -> service,
        `kubectl -n data rollout status statefulset/redis --timeout=120s`; (3) apply mongodb
        configmaps -> statefulset -> service, wait rollout; (4) apply the mongo init Job, `kubectl -n
        data wait --for=condition=complete job/mongodb-init --timeout=120s`.
      - Idempotent (re-apply is a no-op when nothing changed); safe to re-run after a partial failure.
      - Verify: on a clean Phase 0 cluster, one `bootstrap-data.sh` run leaves both StatefulSets Ready,
        the init Job Complete, three PVCs Bound.

    - Step 6 - Makefile wiring
      - New targets (.PHONY; reuse the top-of-file `KUBECONFIG`):
        `make secrets-data`   -> scripts/data-secrets.sh
        `make data`           -> scripts/bootstrap-data.sh
        `make verify-phase1`  -> scripts/verify-phase1.sh
        `make phase1`         -> data verify-phase1
      - All three fail fast via `_need-kubeconfig` if ./kubeconfig is missing.
      - `make lint`: add the new scripts to the shellcheck list and `k8s/data/` to the
        `kubectl apply --dry-run=server` set.
      - `make help`: add the Phase 1 lines.

    - Step 7 - Verification script (scripts/verify-phase1.sh) - the 100% gate
      - `set -euo pipefail`; source lib.sh; `load_env`; `require_vars` the six Phase 1 vars; KUBECONFIG
        from lib. `fail() { die "verify-phase1: $*"; }`. Numbered `[n/N]` logs like verify-phase0.sh.
      - [1] Both StatefulSets exist and are Ready (`kubectl -n data rollout status`, 1/1 each).
      - [2] Secrets `mongodb-credentials` (5 keys) and `redis-password` (1 key) exist with the
        expected keys (check keys, never print values).
      - [3] PVCs `data-mongodb-0` and `data-redis-0` are Bound.
      - [4] Redis round-trip from a throwaway pod: `redis-cli -h redis.data.svc -a <pw>` SET/GET/DEL;
        assert a no-AUTH command is refused (`NOAUTH`).
      - [5] MongoDB round-trip from a throwaway pod: connect as the app user to the app DB, insert +
        read + drop a doc in a scratch collection; assert the app user CANNOT create a new database /
        do an admin command (least-privilege holds).
      - [6] Persistence: `kubectl -n data delete pod mongodb-0 redis-0`; wait both Ready again; the
        Redis key written pre-delete (with a short TTL beyond the test window) and a Mongo doc written
        pre-delete are both still readable -> data survived the restart on the same PVC.
      - Clean up every throwaway pod / scratch key / scratch collection (trap EXIT, like verify-phase0.sh).
      - Exit non-zero with a clear message on the first failed assertion; print "PHASE 1 OK" on success.

    - Step 8 - Clean-cluster dry run
      - On a cluster that has passed Phase 0: fill the six Phase 1 vars in `.env`
        (`openssl rand -base64 24` for the three passwords), then `make phase1` -> "PHASE 1 OK".
      - Re-run `make verify` (Phase 0 gate) -> still "PHASE 0 OK" (Phase 1 did not regress the substrate).
      - Multi-node: confirm `mongodb-0` / `redis-0` schedule on whichever node the scheduler picks and
        the throwaway test pods on the other node still reach them by `*.data.svc` DNS.
      - Tag `phase-1-complete` once `make phase1` is green from a clean Phase 0 cluster and
        `verify-phase1.sh`'s persistence check (Step 7 [6]) passes.

    - Definition of done (Phase 1)
      - Every file in "Files (Phase 1 - Data layer)" exists with real content (no STUB markers),
        plus `k8s/data/mongodb/init-job.yaml` (added in Step 4).
      - On a Phase 0 cluster: `make phase1` -> "PHASE 1 OK" and `make` exits 0; `make verify` still
        prints "PHASE 0 OK".
      - `mongodb.data.svc` and `redis.data.svc` resolve cluster-wide; a pod on any node authenticates
        and does I/O against both.
      - Deleting `mongodb-0` / `redis-0` loses no data (PVC-backed); the app user is least-privilege.
      - No secret values in git, in ConfigMaps, or echoed by any script; new scripts pass `bash -n`
        (shellcheck where available); `k8s/data/` passes `kubectl apply --dry-run=server`.
      - README gains a "Phase 1 - Data layer" section: the six `.env` vars, `make phase1`, expected
        `verify-phase1.sh` output, and how to connect a client from inside the cluster.

- Build Order (dependency-ordered; each layer stands on a working one below it)
  - Core chain: k3s → container registry → Kong → one real service → MongoDB/Redis → auth → CI/CD → observability → TLS → backups → maintenance
  - Phase 0 - Substrate
    - Cluster: k3s SERVER on a Linux host (`make cluster`); each extra Linux machine joins with
      `scripts/node-join.sh` (see Diagram > horizontal-scale). kubectl working, default StorageClass
      (local-path), PVCs bind.
    - Container registry: none in Phase 0 - workers pull from public registries. The real authenticated
      in-cluster registry is deferred to Phase 5 (behind Kong + TLS).
    - Namespace split + secrets convention (no K8s secrets in Phase 0; k3s join token cached under .secrets/).
  - Phase 1 - Data layer  (`make phase1`; gate: verify-phase1.sh -> "PHASE 1 OK")
    - First K8s Secrets: scripts/data-secrets.sh (mongodb-credentials, redis-password) from .env,
      idempotent, plugs into the Phase 0 create-secrets.sh convention.
    - Redis first (redis:7.2-alpine, StatefulSet + PVC, requirepass, AOF + RDB, noeviction) -
      needed by BullMQ and Kong rate-limiting.
    - Then MongoDB (mongo:7.0, StatefulSet + PVC, auth on, root from secret + one-shot init Job that
      creates a least-privilege app user/DB). Single instance, no replica set yet (Phase 6).
    - Headless Services mongodb.data.svc / redis.data.svc; no Kong in front yet (Phase 2) - reached
      only from in-cluster pods. verify-phase1.sh proves auth, least-privilege, and PVC persistence
      across a pod delete.
  - Phase 2 - Edge
    - Kong (declarative/DB-less mode; routes / and /api/*) - integration point for auth, TLS, rate limiting, maintenance
    - One trivial backend service (/api/ping) - end-to-end smoke test for every later change
    - Frontend (React + NGINX image; Kong routes / to it)
  - Phase 3 - Identity ✅ COMPLETE
    - Auth service (Passport.js + JWT) issues tokens; backend services verify tokens via shared middleware
    - Test IDOR / deny-by-default here
  - Phase 4 - Async work ✅ COMPLETE
    - BullMQ workers (separate Deployment, pulls from Redis) with jobs-api for job management
    - Auto-scaling workers (1-10 replicas), retry logic, IDOR prevention, graceful shutdown
  - Phase 5 - Operate  (three sub-gated tracks, built 5A -> 5B -> 5C; `make phase5` chains them)
    - 5A TLS: cert-manager + Kong HTTPS listener (`make tls`; gate: verify-phase5a.sh -> "PHASE 5A OK")
      First, because Phase 3 JWTs currently ride plain HTTP. Does NOT need a real domain: TLS_MODE
      defaults to `selfsigned` and works on the NodePort IP; adding a domain later is an .env edit
      plus `make tls`, with the cert secret name fixed so no other wiring changes.
    - 5B Observability: PLG stack + services/common/metrics.js (`make obs`; gate -> "PHASE 5B OK")
      Second, so CI/CD is built with metrics and logs already available to debug it. Delivers the
      BullMQ queue-depth metric Phase 4's HPA anticipated (wiring the HPA to it is a later phase).
    - 5C CI/CD + registry: Gitea + Drone + the in-cluster container registry (`make ci`; -> "PHASE 5C OK")
      Last, and the only track that mutates earlier phases: it cuts all six service Deployments off
      the public REGISTRY_URL onto the Gitea registry, discharging the "deferred to Phase 5" promise
      made in the Phase 0 and Phase 2 notes. REGISTRY_MODE=external is the tested rollback.
      DEFERRED BY CHOICE (2026-09-11) - built but not adopted; the `ci` namespace was deleted and
      REGISTRY_MODE remains `external`. The Phase 0/Phase 2 registry promise therefore still stands
      open. See the STATUS block under "Files (Phase 5 - Operate)" for the reasoning and for what is
      known about the one aborted `make ci` run.
      REMOVED FROM MASTER (2026-09-12): the code itself (ci/, k8s/ci/, bootstrap-ci.sh,
      verify-phase5c.sh, gitea-secrets.sh, registry-secret.sh, deploy-key.sh, the `make ci`/
      `verify-phase5c` targets, REGISTRY_MODE/GITEA_*/DRONE_RPC_SECRET) no longer exists on
      `master` - preserved as-is on branch `phase-5c-cicd` if ever revisited. See the 2026-09-12
      SESSION UPDATE at the end of this file.
  - Phase 6 - Resilience & lifecycle
    - 6A Backup/DR (`make phase6a`; gate: verify-phase6a.sh -> "PHASE 6A OK") - IMPLEMENTED,
      VERIFIED end-to-end against real AWS S3 (2026-09-12): all 7 checks pass, including the real
      restore round-trip (sentinel written, backed up, destroyed, restored, confirmed). See the
      2026-09-12 SESSION UPDATE at the end of this file for the bug that surfaced (the gate's own
      cleanup deleting the backup on a failed restore) and the fix.
      Nightly mongodump + Redis RDB CronJobs uploading to EXTERNAL S3-compatible storage, restore
      scripts, retention pruning, PodDisruptionBudgets. The only Phase 6 track that closes a real
      exposure: MongoDB is a single replica on node-bound local-path with no copy anywhere, so
      losing that disk loses every account, token and job record. The gate performs an ACTUAL
      restore and compares content - a backup that has never been restored is a hypothesis.
      Deliberately excludes Mongo HA and point-in-time recovery; see the plan for why.
    - 6B Maintenance page (`make phase6b`; gate: verify-phase6b.sh -> "PHASE 6B OK") - IMPLEMENTED
      2026-09-11, VERIFIED on cluster `pavilion` 2026-09-11: `./scripts/verify-phase6b.sh
      --i-know-this-causes-downtime` -> "PHASE 6B OK" (6/6), including the disruptive on/off cycle
      against the live gateway. Two real bugs only surfaced by actually running it:
        - `make build-push` reused a stale Docker layer for `services/auth/src`, so the auth image
          it pushed was missing `routes/maintenance.js` entirely - `make build-push` reported
          success while shipping stale code. Worked around with `docker build --no-cache`;
          `build-push.sh` itself still has no cache-busting (open item, see README troubleshooting).
        - The gate's ACME-bypass check curled `cm-acme-http-solver` live, which only has a real
          upstream mid-challenge; on this cluster (TLS_MODE=selfsigned) it doesn't exist between
          renewals, so Kong 503s on it for an unrelated reason (no upstream) and the check
          false-failed. Fixed to assert the route is present in Kong's applied config instead of
          probing it live.
      The 5C dependencies were designed out rather than worked around:
        - No built image. The page is a ConfigMap (HTML + nginx.conf) mounted into stock
          nginx:1.25-alpine, so there is no Dockerfile, no build-push, and no registry - and
          editing the page is `kubectl apply` instead of a rebuild.
        - No notify.sh. Maintenance is a deliberate operator action, not an alert.
      Design points worth keeping: the page pod runs ALWAYS (toggling is a Kong routing swap, not a
      pod start - an image pull is the wrong thing to find broken when you need the site down); the
      state ConfigMap stores the SAVED Kong config, so `off` restores exactly what was there rather
      than rebuilding routes and silently dropping grafana/git; and the bypass list
      (/api/auth/login, /internal/maintenance, ACME) is the anti-lockout guarantee that the gate
      tests explicitly. The auth service gained an admin-role-gated POST /internal/maintenance/off
      backed by RBAC scoped to two named ConfigMaps plus restarting Kong - the gate asserts that SA
      cannot read secrets in app/data/platform. There is deliberately no HTTP way to turn
      maintenance ON. Queue pausing is opt-in (--pause-queues), global via Redis so HPA-started
      workers are covered, and lets in-flight jobs finish.
      The gate's on/off cycle is disruptive (~60s of 503s) and skipped unless
      --i-know-this-causes-downtime is passed; without it it prints PHASE 6B PARTIAL.
    - 6C Provisioned worker fleet (Terraform + cloud-init self-join, `make workers COUNT=n`) -
      NOT PLANNED. Independent of the other two; worth building when one machine stops being enough.
  - Cross-cutting (from commit #1, never "done")
    - Security guidelines: enable security-guidance plugin + CI checks (secret scanning,
      no exec(), parameterized queries) as soon as a repo exists
  - Minimum viable spine: k3s → registry → MongoDB + Redis → Kong → one placeholder service

- Phase 0 - what is accomplished
  The substrate everything else runs on. `make phase0` on a Linux host delivers:
  1. A k3s cluster - k3s server installed on the host (embedded etcd; Traefik disabled, Kong comes later).
  2. Horizontal scale built in - any other Linux machine joins as a worker with one command
     (`make node-join TARGET=user@ip`) over a WireGuard-encrypted overlay. The scheduler spreads pods
     across all nodes; services reach each other by DNS regardless of which machine they land on.
  3. Working storage - `local-path` set as the default StorageClass, so PVCs bind with no annotation.
  4. Namespace layout - `platform` / `data` / `app`.
  5. A secrets convention - no secrets yet, but `create-secrets.sh` is the stable entrypoint later
     phases plug into; the k3s join token is cached to `.secrets/` (gitignored).
  6. An acceptance gate - `make verify` asserts nodes Ready, default SC correct, namespaces present,
     a PVC binds, and every node can pull an image -> prints "PHASE 0 OK".
  Plus repo scaffolding: Makefile, .env.example, .gitignore, README.md, architecture.txt.
  NOT included (deferred by design): the authenticated image registry, Kong, databases, TLS - Phases 1-5.
  Status: implemented; scripts pass `bash -n`. End-to-end run (server + a joined worker) is Step 7,
  pending real Linux hosts, before tagging `phase-0-complete`.

- Phase 2 - what is accomplished

  - Phase 3 - Auth: develop from 0 -> 100 (instantiate every file, then code it, then verify)
    - Scope: JWT-based authentication via an Express + Passport.js auth service that issues RS256
      tokens (access + refresh). Users stored in MongoDB (Phase 1), refresh tokens in Redis (Phase 1).
      Kong (Phase 2) routes /api/* requests without authentication at gateway level. Backend services
      gain a shared authContext middleware (services/common/authContext.js) to verify JWT tokens,
      extract user identity, and enforce object-level authorization (prevent IDOR). Frontend gains
      login/register forms and token management.
      No TLS yet (Phase 5) - tokens ride HTTP, Kong enforces on plain 30080.

    - Runtime decision: RS256 (asymmetric) JWT so backend services can verify with the public key
      without sharing the signing key. Access tokens short-lived (15 min), refresh tokens stored in Redis
      with rotation on use. Passwords hashed with argon2 (or bcrypt fallback). Backend services verify
      tokens using shared authContext middleware, not at Kong gateway. The auth service is a separate
      deployment in `app` ns alongside ping/frontend. Shared authContext module lives in
      /services/common/ and is copied into every backend service's Docker build.

      - Bottom-up by depends_on: never create a file before the files it depends on are in place.
      - Two passes per file: (1) instantiate with a header comment (purpose + depends_on, body a STUB
        marker); (2) implement - real content, remove the STUB marker.

        full chain `make phase3` exits 0 on a cluster that has passed Phase 0, Phase 1, and Phase 2.
      - Security: never eval(), no shell interpolation with user input; secrets only via .env +
        k8s Secrets; scripts `set -euo pipefail`, source `scripts/lib.sh`, never echo secret values;
        argon2/bcrypt for passwords, RS256 for JWTs, IDOR checks in every object-access path.

    - Step 3 - User model (services/auth/src/models/user.js)
      - Mongoose schema: email (unique, required, lowercase), passwordHash (required, never selected
        by default), roles[] (default ['user']), createdAt, updatedAt.
      - Pre-save hook: if password is modified, hash with argon2 (`await argon2.hash(password)`);
        if argon2 unavailable, fallback to bcrypt (`await bcrypt.hash(password, 10)`).
      - Instance method `comparePassword(candidatePassword)`: returns
        `await argon2.verify(this.passwordHash, candidatePassword)` (or bcrypt.compare fallback).
      - Connect to MongoDB using the Phase 1 least-privilege app user (mongodb-credentials from
        secret, MONGO_APP_USER / MONGO_APP_PASSWORD / MONGO_APP_DB from env).

    - Step 4 - Token store (services/auth/src/tokenStore.js)
      - Redis-backed refresh token allowlist. On login, `storeRefreshToken(userId, tokenId, ttl)`
        stores `SET refresh:<tokenId> <userId> EX <ttl>`.
      - On refresh, `validateRefreshToken(tokenId)` checks `GET refresh:<tokenId>`; if present,
        deletes it (single-use rotation) and returns the userId; caller issues a new refresh token.
      - On logout, `revokeRefreshToken(tokenId)` runs `DEL refresh:<tokenId>`.
      - Connects to Redis using the Phase 1 redis-password (REDIS_PASSWORD from env, host redis.data.svc).
      - Structured logging: never log token values, only tokenId prefixes (first 8 chars).
      - Verify: store a token, validate (succeeds once, fails on second call = rotation), revoke
        another token and validate (fails).

    - Step 5 - Passport strategies (services/auth/src/passport.js)
      - Local strategy (passport-local): verify email + password via User.findOne + comparePassword;
        return user object on success, false on failure.
      - JWT strategy (passport-jwt): extract from `Authorization: Bearer <token>` header, verify
        with RS256 public key loaded from the mounted jwt-keypair secret
        (`/secrets/jwt/public-key`), return decoded payload. Used for /api/auth/me and internal
        auth checks (though Kong does the primary verification).
      - Export configured passport instance.
      - Verify: local strategy authenticates a valid user and rejects invalid password; JWT strategy
        verifies a token signed with the private key.

      - GET /api/auth/me: passport.authenticate('jwt'), return user profile (no passwordHash).

- Phase 3 - what is accomplished
  JWT-based authentication and authorization. `make phase3` on a Phase 2 cluster delivers:
  1. Auth service - Express + Passport.js backend (POST /api/auth/register, /login, /refresh, /logout,
     GET /api/auth/me), issues RS256 access tokens (15 min) + refresh tokens (7 days), 2 replicas in
     `app` namespace. Users stored in MongoDB (argon2 password hashing), refresh tokens in Redis
     (single-use rotation).
  2. JWT keypair - RS256 2048-bit keys generated by `scripts/jwt-keys.sh`, stored in k8s Secrets
     (jwt-keypair in `app` ns for auth service signing).
  3. Kong routing - declarative config routes all /api/* requests to backend services without
     authentication at gateway level. Backend services handle token verification themselves.
  4. Shared auth middleware - authContext.js in services/common/ provides requireAuth() to verify
     JWT tokens, requireRole() for role-based access, assertOwnership() to prevent IDOR.
     Each service includes this middleware and verifies Authorization: Bearer tokens directly.
     Available to all backend services via /services/common/.
  5. Protected routes - ping service updated to require auth (requireAuth middleware). All /api/ping
     requests now need a valid JWT; the ping service itself verifies tokens and returns 401 on invalid/missing tokens.
  6. Frontend auth UI - login/register forms, token storage in localStorage, auto-inject
     `Authorization: Bearer` header on fetch, auto-refresh on 401 (refresh token rotation), logout
     clears tokens. Logged-in UI shows /api/ping result; logged-out redirects to login.
  7. Token security - access tokens short-lived, refresh tokens stored in Redis allowlist (not JWT
     storage), single-use rotation on refresh, revoked on logout. Passwords never logged or echoed.
  8. Verification gate - `make verify-phase3` tests registration, login, /me with token, /me without
     token = 401, /api/ping with token = 200, /api/ping without token = 401, refresh rotation,
     logout revocation -> prints "PHASE 3 OK".
  Plus Makefile targets (`make phase3`, `make jwt-keys`, `make auth`), .env Phase 3 block
  (JWT expiry config), updated kong-configmap.yaml (JWT plugin), and README Phase 3 guide.
  NOT included (by design): TLS/HTTPS (Phase 5 - tokens currently ride HTTP), role-based UI
  (admin panel comes later), password reset flow (documented as Phase 3.5 extension), MFA
  (documented as Phase 3.5 extension).
  Status: ✅ COMPLETE (2026-09-09). Deployed and verified on phase-3-auth branch.
  Note: Kong JWT plugin removed in favor of backend service authentication - Kong routes requests,
  backend services verify tokens using shared requireAuth middleware from services/common/.

- Phase 4 - Async work: develop from 0 -> 100 (instantiate every file, then code it, then verify)
    - Scope: Add asynchronous background job processing using BullMQ (backed by Redis from Phase 1).
      Two new services: (1) jobs-api - REST API for creating and monitoring jobs (auth-protected via Phase 3),
      (2) worker - separate Deployment that pulls jobs from the queue and processes them. Jobs stored
      durably in MongoDB beyond Redis retention. This proves the full async pattern: API enqueues →
      Redis queue → worker processes → writes result to Mongo → API can fetch status/result.
    - Runtime decision: BullMQ for queue management (mature, Redis-backed, built-in retry/progress/events),
      separate worker Deployment (not part of web services, scales independently), HPA for auto-scaling
      workers based on CPU (and later queue depth from Phase 5 observability). Job ownership tied to
      authenticated user (req.user.id from Phase 3) for IDOR prevention. Jobs have unique IDs, status
      tracking (pending/active/completed/failed), retry with exponential backoff, and graceful shutdown
      (SIGTERM drains in-flight jobs).
    - This is the FIRST phase that uses Redis as a queue (not just a cache). `services/common/queue.js`
      is the shared BullMQ setup consumed by both jobs-api (producer) and worker (consumer). Pattern:
      all job types in one queue, worker dispatches by job.name to handlers/ directory (one file per type).
    - Example job types for this phase: (1) "hello-world" - trivial async task that sleeps then returns
      a greeting (proves the basic flow), (2) "failing-job" - always throws an error (proves retry logic),
      (3) optional: "slow-job" with progress updates (proves job.updateProgress()).

- Phase 4 - what is accomplished
  Asynchronous background job processing using BullMQ (backed by Redis from Phase 1). `make phase4` on a Phase 3 cluster delivers:
  1. jobs-api service - Express + BullMQ producer (POST /api/jobs to create, GET /api/jobs/:id for status,
     GET /api/jobs to list), auth-protected via requireAuth from Phase 3, 2 replicas in `app` namespace.
     Jobs stored in MongoDB (jobId, ownerId, type, status, data, result, timestamps) beyond Redis retention.
  2. worker service - BullMQ consumer Deployment (separate from web services), pulls jobs from Redis queue,
     dispatches by job.name to handlers/ directory (helloWorld, failingJob example handlers included),
     updates job status in MongoDB, auto-scales 1-10 replicas via HPA (CPU 70%), graceful shutdown
     (60s terminationGracePeriod drains in-flight jobs).
  3. Shared queue library - services/common/queue.js provides createQueue/createWorker/createQueueEvents,
     JOB_TYPES enum, default retry config (3 attempts, exponential backoff 2s/4s/8s). Available to all
     services for async work.
  4. Kong routing - declarative config adds /api/jobs route to jobs-api service (auth handled by jobs-api
     itself, not Kong). No rate-limiting plugin yet (Phase 5).
  5. Job ownership - jobs tied to req.user.id (from Phase 3 JWT), IDOR prevention (user A cannot read
     user B's jobs via GET /api/jobs/:id → 403), verified in verify-phase4.sh.
  6. Retry logic - failed jobs retry 3 times with exponential backoff (2s, 4s, 8s) then status → failed.
     BullMQ handles retry automatically. verify-phase4.sh tests this with failing-job handler.
  7. Worker resilience - killing worker pods mid-job does not lose jobs (another worker or restarted pod
     picks it up). Verified in verify-phase4.sh [6/7].
  8. Verification gate - `make verify-phase4` tests 7 scenarios: deployments healthy, job creation,
     completion polling, retry logic, IDOR prevention, worker resilience, job listing → prints "PHASE 4 OK".
  Plus Makefile targets (`make phase4`, `make jobs`, `make verify-phase4`), README Phase 4 section
  (usage examples, adding custom job types, troubleshooting), updated Kong config.
  NOT included (by design): Queue-depth based auto-scaling (Phase 5 observability adds custom metrics),
  rate-limiting on job creation (Phase 5), job priority UI (future), job progress updates (handler can
  report progress but no UI yet).
  Status: ✅ COMPLETE (2026-09-10). Deployed and verified on master branch.
  Note: Redis maxmemory-policy from Phase 1 is `noeviction` to ensure BullMQ jobs are never evicted.
  Jobs stored in MongoDB provide durability beyond Redis; BullMQ purges completed jobs after
  removeOnComplete: 100 limit.

- Phase 5 - Operate: develop from 0 -> 100 (instantiate every file, then code it, then verify)
    - Scope: make the platform operable rather than merely running. Three tracks, built in this order:
      5A TLS (cert-manager + Let's Encrypt, HTTPS at Kong), 5B Observability (PLG stack + per-service
      metrics), 5C CI/CD (Gitea + Drone + the in-cluster container registry, and the cutover of all six
      service Deployments off the public registry onto it). Each track has its own bootstrap script,
      its own Makefile target, and its own sub-gate; `make phase5` chains all three.
    - Ordering rationale: TLS is the smallest track and closes the largest open hole - Phase 3 JWTs
      currently ride plain HTTP on :30080. Observability comes second so the CI/CD track is built with
      metrics and logs already available to debug it (and it delivers the queue-depth metric Phase 4's
      HPA was written to consume). CI/CD is last because it depends on both: pipelines publish build
      metrics to 5B, and the Gitea registry is served over the 5A TLS listener.
    - Sub-gates: each track ends in its own verification script and can be stopped after cleanly.
        make tls -> scripts/verify-phase5a.sh -> "PHASE 5A OK"
        make obs -> scripts/verify-phase5b.sh -> "PHASE 5B OK"
        make ci  -> scripts/verify-phase5c.sh -> "PHASE 5C OK"
        make phase5 = tls obs ci verify-phase5   (verify-phase5.sh re-runs all three -> "PHASE 5 OK")
      This is a deliberate departure from Phases 0-4 (one gate each). Phase 5 is roughly forty files
      across three unrelated subsystems; a single all-or-nothing gate would make a partial failure
      undiagnosable and would block TLS behind a broken Drone runner.

    - Runtime decision: TLS - cert-manager installed from its pinned static manifest (no Helm, matching
      the no-Helm rule from Phase 1), HTTP-01 solver routed through the existing Kong proxy. Observability
      - PLG deployed as plain manifests (no kube-prometheus-stack operator, same rule); Loki single-binary
      with filesystem storage on local-path; Promtail as a DaemonSet so every joined node ships logs
      without per-node configuration. CI/CD - Gitea with its built-in container registry (one component
      instead of Gitea + a separate Docker registry), Drone with the Kubernetes runner so build steps
      are pods scheduled onto the existing worker fleet.
    - Namespaces: uncomment `observability` and `ci` in k8s/base/namespaces.yaml (Phase 0 Step 3 left
      them commented for exactly this phase). cert-manager creates its own `cert-manager` ns.
      `make base` must be re-run before 5B/5C, and verify-phase0.sh's namespace check extended to
      accept the two new namespaces without requiring them (they are absent on a Phase 0-4 cluster).

    - DOMAIN IS OPTIONAL AND PLUG-AND-PLAY (the governing constraint on Track A)
      The whole phase must come up, pass its gates, and stay useful on a cluster with no domain at all,
      and acquiring a domain later must be a config edit plus one command - never a rebuild, never a
      manifest edit, never a re-issue of anything but the certificate. Concretely:
      - `.env` gains TLS_MODE with three values. Every manifest and script branches on this one variable
        and nothing else:
          TLS_MODE=selfsigned   (default) cert-manager SelfSigned ClusterIssuer mints a cert for the
                                node IP + `backbone.local`. HTTPS works immediately on the NodePort;
                                browsers warn. No DNS, no internet egress to ACME, no rate limits.
          TLS_MODE=staging      ACME staging ClusterIssuer. Requires DOMAIN set and resolving. Untrusted
                                chain, but exercises the real HTTP-01 path against a rate-limit-free
                                endpoint. This is the rehearsal step, not a destination.
          TLS_MODE=production   ACME production ClusterIssuer. Requires DOMAIN set and resolving.
      - The Certificate object's dnsNames are templated from DOMAIN by bootstrap-tls.sh, and its
        `secretName` is the SAME (`kong-tls-cert`) in all three modes. Kong's TLS listener therefore
        references one fixed secret name and never changes when the mode changes - swapping issuers
        rewrites the contents of that secret, not the wiring around it.
      - Adding a domain later is exactly: set DOMAIN + TLS_MODE=staging in .env -> `make tls` -> confirm
        -> set TLS_MODE=production -> `make tls`. cert-manager reissues into the same secret; Kong picks
        it up. No pod rebuild, no manifest change, no other phase touched.
      - Every Kong route added in 5B/5C (grafana, git) is defined as a PATH on the existing proxy
        (`/grafana`, `/git`) with the host-based form (`grafana.<domain>`) written alongside it and
        activated by bootstrap scripts only when DOMAIN is a real resolvable name. A domainless cluster
        gets working URLs; a domained one gets pretty ones. No route is domain-only.
      - verify-phase5a.sh asserts the correct behaviour FOR THE CURRENT MODE (selfsigned: cert present
        and served, chain untrusted-but-valid; production: chain trusted and issuer is Let's Encrypt).
        It must never fail a domainless cluster for lacking a domain.

        404 from Kong and cert-manager retries until the ACME order times out. This is the single most
        likely failure in Track A; call it out in the script's own error message.

      - Order: (1) cert-manager-install.sh; (2) apply the ClusterIssuer for TLS_MODE, wait Ready=True;
        (3) render + apply certificate.yaml with the mode's dnsNames; (4) merge the TLS block into
        kong-configmap.yaml, apply, update the Kong Deployment + proxy Service; (5) wait for the
        Certificate to become Ready (up to ~180s for ACME - self-signed is instant); (6) rollout-restart
        Kong and wait; (7) print the HTTPS endpoint and, when TLS_MODE=selfsigned, the one-liner to
        upgrade to a real domain later.
      - Idempotent, and specifically re-runnable ACROSS modes: running it again with a changed TLS_MODE
        must converge (apply the new issuer, repoint the Certificate's issuerRef, let cert-manager
        reissue into the same secret, restart Kong). This is the plug-and-play path - test it explicitly.
      - Verify: on a domainless cluster `make tls` -> HTTPS live with a self-signed cert. Then set
        DOMAIN + TLS_MODE=staging, re-run, and confirm the cert is reissued by the staging CA with no
        other change.

  Deviations from the plan above, decided during implementation:
   - Kong's TLS listener is patched on by bootstrap-tls.sh rather than shipped in deployment.yaml.
     Kong refuses to start when an `ssl` listener is declared with no certificate present, which would
     have made cert-manager a hard prerequisite for the Phase 2 gateway. The committed Deployment
     stays HTTP-only so Phase 2 still stands alone; the kong-tls-cert mount is `optional: true`.
   - The self-signed path issues a real CA + leaf (clusterissuer-selfsigned.yaml creates a SelfSigned
     bootstrap issuer, a CA Certificate, then a CA ClusterIssuer) rather than a bare self-signed leaf,
     which some clients reject outright. It also exercises the same chain-building code as ACME.
   - Kong declarative routes are merged by `kong_insert_block()` in lib.sh, not by `awk -v`: BSD/macOS
     awk rejects embedded newlines in a -v assignment, so the awk form silently injected nothing on a
     macOS control host. The marker is matched at column 0 (`^plugins:`) because kubectl strips the
     block-scalar indent when reading kong.yaml back out of the ConfigMap.
   - build-push.sh now builds all five services (jobs-api and worker were never added in Phase 4) and
     selects the Docker build context per service - ping/jobs-api/worker need the repo root because
     they COPY services/common; frontend/auth use their own directory. One shared context breaks two
     of them either way.
   - verify-phase5b [6] asserts the alerting PIPELINE (Alertmanager connected, rule groups loaded)
     rather than firing a synthetic alert, which would require mounting a rule into Prometheus and
     restarting it to test the same two failure modes.
   - The in-cluster registry needs `/etc/rancher/k3s/registries.yaml` on every node (it is plain HTTP
     inside the cluster). registry-secret.sh prints the exact file; this is manual, per-node, and is
     the most likely cause of ImagePullBackOff after setting REGISTRY_MODE=incluster.
   - services/auth switched to a repo-root Docker build context so it can COPY services/common; it
     was the one backend service that never imported the shared modules. build-push.sh knows this
     (only the frontend still builds from its own directory).
   - Instrumentation IS wired: prom-client added to ping/auth/jobs-api/worker, instrumentHttp() in
     the three Express services, /metrics folded into the worker's existing health server (its
     mongo+worker readiness logic was better than the generic one in metrics.js), job counters and
     duration recorded around the handler, and the queue-depth gauge polled from the worker. The
     prometheus.io/scrape annotations are on all four pod templates.

- Phase 6A - Backup / Disaster Recovery: develop from 0 -> 100
    - Scope: scheduled, restorable, OFF-SITE backups of MongoDB and Redis, plus the disruption
      budgets that keep the platform up during node drains. Tracks B (maintenance mode) and C
      (Terraform worker fleet) are NOT in scope - see "Why only Track A" below. `make backup`
      brings it up; `make verify-phase6a` is the gate -> "PHASE 6A OK".
    - Why only Track A: it is the one Phase 6 track that closes a real exposure rather than adding
      a convenience. Today MongoDB is a single replica on `local-path` - node-bound storage with no
      copy anywhere. Losing that disk loses every user account, refresh token and job record, with
      no recovery path. Track B matters when there are users to apologise to; Track C matters when
      one machine stops being enough. Neither is true yet. Both stay in the Files manifest below,
      unbuilt, and both need rework first (Track B's bootstrap assumed Phase 5C's notify.sh and
      image registry, and 5C is deferred).

    - Runtime decision: backups go to EXTERNAL S3-compatible object storage (AWS S3, Backblaze B2,
      Cloudflare R2 - any endpoint that speaks the S3 API). This is the decision that makes the
      phase worth doing:
        - A backup on the same node as the database is not a backup. It protects against a dropped
          collection or a bad migration; it does nothing about the disk dying, which is the failure
          that actually ends the platform. The existing manifest sketched a `backup-pvc` and an
          optional in-cluster MinIO - on a single node MinIO shares the same physical disk, so it
          adds machinery without adding durability. Both are superseded here.
        - A local PVC is still used, but only as a STAGING area: dump to the PVC, upload, verify the
          upload, then prune. That way a failed upload leaves the dump recoverable by hand rather
          than losing the window entirely.
      Cost is a few dollars a month and one external credential. That is the price of the platform
      surviving its own hardware.
    - Runtime decision: plain k8s CronJobs running the official `mongo:7.0` and `redis:7.2-alpine`
      images plus `amazon/aws-cli` for the upload. No operator, no Velero - consistent with the
      no-Helm/no-operator rule held since Phase 1. Velero backs up cluster OBJECTS; what is actually
      irreplaceable here is the DATA inside two StatefulSets, which mongodump/RDB handle directly.

    - What Phase 1 already gives us (do NOT rebuild):
      - Redis persistence is ALREADY configured in k8s/data/redis/conf-configmap.yaml: RDB save
        points (900 1 / 300 10 / 60 10000), `appendonly yes`, `appendfsync everysec`. The old
        manifest's `redis-persistence-patch.yaml` is therefore redundant and is dropped from this
        plan. Redis needs a backup JOB, not a persistence change.
      - `mongodb-credentials` (root-* and app-*) and `redis-password` exist in ns `data`. Backups
        use the ROOT credential, deliberately: the app user is scoped readWrite on one database and
        cannot read `admin`, so an app-user mongodump would silently omit users and roles.

    - Guiding rules (same as Phases 0-5)
      - Bottom-up by depends_on; two passes per file (headered stub, then real content).
      - Nothing is "done" until `make verify-phase6a` prints "PHASE 6A OK" on a live cluster.
      - Secrets only from .env via the create-secrets.sh convention; never echoed. The S3 secret
        key is a credential with write access to your backups - treat it like the Mongo root password.
      - Phases 0-5 stay green: `make verify`, `verify-phase1`, `verify-phase3`, `verify-phase4`,
        `verify-phase5a`, `verify-phase5b` all keep passing.
      - RESTORE IS PART OF THE FEATURE. A backup that has never been restored is a hypothesis. The
        gate performs a real restore into a scratch database and compares content - not a file
        listing, not an exit code.

      - CronJob `mongo-backup`, schedule from BACKUP_SCHEDULE_MONGO, concurrencyPolicy: Forbid
        (two dumps must never race onto one staging PVC), backoffLimit 2,
        successfulJobsHistoryLimit 3, failedJobsHistoryLimit 3, startingDeadlineSeconds 3600.
      - Two containers, sequenced as initContainer -> container so the upload cannot run on a
        failed dump:
        (1) `mongo:7.0` - `mongodump --uri="mongodb://$ROOT_USER:$ROOT_PASS@mongodb.data.svc:27017"
            --authenticationDatabase=admin --archive=/staging/mongo-<ts>.gz --gzip`.
            Credentials from secretKeyRef mongodb-credentials/root-*, passed as env and referenced
            as "$VAR" inside the container - never interpolated into the manifest.
            Uses --archive (single file) rather than a directory dump: one object to upload, one to
            verify, and mongorestore reads it directly.
        (2) `amazon/aws-cli:2` - `aws s3 cp` the archive to
            s3://$BUCKET/$PREFIX/mongo/<ts>.gz (with --endpoint-url when BACKUP_S3_ENDPOINT is set),
            then `aws s3api head-object` to CONFIRM it landed and the size matches the local file,
            then delete the local archive. Finally prune objects older than BACKUP_RETENTION_DAYS.
      - The verify-then-delete order matters: never remove the only copy before proving the remote
        one exists.
      - Verify: `kubectl -n data create job --from=cronjob/mongo-backup test` completes; the object
        appears in the bucket with a non-zero size.

    - Step 5 - Redis backup CronJob (k8s/data/backup/redis-cronjob.yaml)

        (1) `redis:7.2-alpine` - `redis-cli -h redis.data.svc -a "$REDIS_PASSWORD" --no-auth-warning
            BGSAVE`, then poll `LASTSAVE` until the timestamp advances (BGSAVE is asynchronous -
            copying immediately captures the PREVIOUS snapshot, a subtle way to back up stale data),
            then `--rdb /staging/redis-<ts>.rdb` to pull a fresh dump over the wire.
            `--rdb` is used rather than reading the PVC directly: the backup job does not need to
            share a volume with the Redis pod, so there is no RWO conflict on local-path.
        (2) same aws-cli upload/verify/prune container, to $PREFIX/redis/<ts>.rdb.
      - Scheduled an hour after Mongo so the two never contend for the staging PVC.
      - Note in the file: Redis holds refresh tokens and the BullMQ queue. Restoring it replays
        old jobs and revives revoked sessions, so a Redis restore is a deliberate act, not routine.
      - Verify: manual trigger completes; object in the bucket; `redis-check-rdb` accepts the file.

  Implementation notes / deviations:
   - Restore Jobs use an aws-cli initContainer that fetches onto a shared emptyDir, then the
     mongo:7.0 container restores from it. Installing the AWS CLI into the mongo image at run time
     would need internet egress on every restore and add a minute to the one operation performed
     under pressure.
   - mongorestore is invoked with --nsFrom/--nsTo so a dump taken from the live database lands in
     the scratch one. Without that rewrite mongorestore writes back to the database the dump came
     from, silently ignoring --target - which would turn a "safe" restore into an overwrite.
   - Redis has no safe in-place restore (no namespace to redirect into), so redis-restore.sh offers
     `inspect` as the default path - it loads the RDB into a throwaway Redis on port 6399 and
     reports DBSIZE and sample keys. The actual restore uses MIGRATE rather than a GET/SET loop, so
     TTLs survive; a naive copy would turn expiring refresh tokens into permanent ones.
   - verify-phase6a builds its kubectl --overrides with jq rather than string interpolation. The
     mongosh expressions contain quotes and braces, and hand-rolled escaping through shell -> JSON
     -> mongosh is exactly where Phase 5's template bugs came from.
   - Check [2] asserts a NEGATIVE: that no PDB exists for mongodb/redis. minAvailable on a
     1-replica workload makes the node permanently undrainable, and the failure mode (drain hangs
     forever with no clear reason) is worth a gate.
   - Both CronJobs verify the remote object's size against the local file BEFORE deleting the local
     copy, so a truncated upload leaves the dump recoverable by hand.

SESSION UPDATE (2026-09-12) - first real external-user install, end to end
===============================================================================
Everything below reflects what was ACTUALLY built, verified, and shipped to
`master` in this session, superseding the planned-but-not-built Track A/B/C
detail above wherever it conflicts (MinIO, Terraform-provisioned workers, and
`make workers` were never built - ignore those blocks; they document a design
that was superseded before implementation). This session's role was a
first-time external user installing the platform end-to-end on real AWS EC2
hardware (single-node, then a second node joined as a worker), fixing every
real bug hit along the way, then building the onboarding flow this always
needed: a guided setup wizard and a single unattended install command.

1. Phase 5C (CI/CD + in-cluster registry) REMOVED from `master`.
   Already DEFERRED BY CHOICE per the 2026-09-11 note above; this session
   went further and deleted the code from `master` entirely (ci/, k8s/ci/,
   scripts/bootstrap-ci.sh, verify-phase5c.sh, gitea-secrets.sh,
   registry-secret.sh, deploy-key.sh, the `make ci`/`verify-phase5c` targets,
   and the REGISTRY_MODE/GITEA_*/DRONE_RPC_SECRET .env vars and the
   `incluster` branch of registry_prefix() in lib.sh) rather than leave a
   dead, unverified code path in the shipped repo. Preserved byte-for-byte
   on a new `phase-5c-cicd` branch if ever revisited. `phase5`/
   verify-phase5.sh now run just 5A + 5B.

2. NEW: `make setup` (scripts/setup-env.sh) - one-time interactive wizard.
   Asks every question the whole install needs, once, up front: K3S_SERVER_ADDR
   (auto-detected), REGISTRY_URL + an optional `docker login` done for you,
   MONGO_ROOT_PASSWORD/MONGO_APP_PASSWORD/REDIS_PASSWORD (Enter to
   auto-generate via `openssl rand -base64 24`, same as every password this
   platform has always needed), TLS_MODE (asks if a real domain exists),
   GRAFANA_ADMIN_PASSWORD (Enter to auto-generate), BACKUP_S3_* (optional -
   skipping just means Phase 6A is skipped later, not degraded), and
   ADMIN_EMAIL (a maintenance-mode admin account, promoted automatically
   later). Writes straight to .env; the user never opens or hand-edits that
   file. Secrets are read with hidden input and never echoed back.
   Hardening added after real user testing: a bare username with no '/' at
   the REGISTRY_URL prompt (a natural mistake) is auto-corrected to
   docker.io/<name> with a message saying so, rather than silently trying to
   `docker login` to a host that doesn't exist; the registry-username prompt
   defaults from the URL already entered instead of asking twice.

3. NEW: `make backbone` - chains every phase unattended: phase0 -> phase1 ->
   phase2 -> phase3 -> phase4 -> tls -> verify-phase5a -> promote-admin ->
   obs -> verify-phase5b -> phase6a (skipped, not degraded, if no
   BACKUP_S3_BUCKET was configured - backup-secrets.sh hard-requires real S3
   credentials even for wiring-only) -> phase6b. 5C stays out per (1) above.
   RESUMABLE: each step writes a stamp file under .backbone-state/
   (gitignored) once it succeeds; a re-run after a mid-way failure skips
   every already-stamped step and resumes at the one that failed, instead of
   redoing completed phases (including their `--no-cache` image rebuilds)
   from scratch. `make backbone-reset` clears the stamps for a genuine
   full re-run.

4. NEW: scripts/promote-admin.sh (`make promote-admin`) - registers
   ADMIN_EMAIL (if set) against the live auth service with a freshly
   generated password (printed once), or promotes it if already registered,
   then sets its Mongo `roles` to include `admin` - so maintenance mode's
   HTTP off-switch (/internal/maintenance) has a real admin account without
   the operator having to run a manual mongosh command by hand. Runs after
   verify-phase5a (needs HTTPS/Kong genuinely up) and before obs.

5. INSTALL_GUIDE.md rewritten from a ~1000-line, 10-step manual walkthrough
   with inline "bug found during this install" writeups down to a short
   quick-start: architecture diagram, prerequisites (exact EC2 spec, the
   inbound firewall table - 22/30443/30080 - with the AWS Console path
   spelled out, make/Docker install), then `make setup` -> `make backbone`
   -> verify. Also documents "Adding a worker node" (see item 8) and the
   public-vs-private-IP browser trap (see item 7). All prior bug writeups
   moved verbatim into this file (below) rather than kept in the user-facing
   guide, which only needs to describe how the install works today.

6. Real bugs found and fixed DURING THIS INSTALL (in addition to the ones
   already recorded above from earlier sessions - Phase 0 cron-quoting,
   namespace over-creation, Mongo URI unescaping, Phase 2's auth-vs-Phase-3
   gate mismatch, Phase 3's build-context/RBAC/cross-namespace-secret/
   URI-escaping stack, Phase 4's disk-pressure and image-naming bugs):
     - verify-phase6a.sh's own `cleanup()` (trap on EXIT) deleted the just-
       created backup object on EVERY exit path, including a FAILED restore
       check - so the moment the restore check failed, cleanup destroyed the
       only evidence needed to debug it (and, on a fresh install, the only
       backup that existed at all). Fixed: only deletes the object once the
       restore is actually proven to work; logs and leaves it in place on
       failure.
     - verify-phase5b.sh checks [1/7] (workload readiness) and [4/7] (Loki
       ingestion) were observed failing on the very first attempt right
       after a fresh bootstrap - not broken, just not finished starting yet
       (Promtail has to scan every pod's log files before shipping anything;
       Loki needs a moment to accept pushes/queries). A single immediate
       check can't tell "still starting" from "actually broken". Both now
       poll for up to 3 minutes before failing for real.
     - verify-phase6a.sh check [3/7] (bucket reachability) hit the same class
       of issue once on a real run: failed on the first attempt with a
       generic "cannot reach the backup bucket", passed instantly on manual
       re-run with unchanged credentials (a fresh throwaway pod's networking
       not warmed up yet). Now retries up to 5 times before failing.
     - .env.example was missing an `SSH_KEY=` line entirely, even though
       node-join.sh documents SSH_KEY as the supported way to point remote-
       mode joins at a specific key. `sed -i "s|^SSH_KEY=.*|...|"` (the only
       sane non-interactive way to set any .env value in this repo) only
       replaces an EXISTING line - with none to match, it silently did
       nothing, and node-join.sh fell back to the default SSH agent/config,
       failing with a bare "Permission denied (publickey)" with no
       indication why. Fixed by adding the line.

7. Real operational trap found (not a code bug): every command in the
   install guide runs ON the instance and addresses it via `hostname -I`
   (the private VPC IP). That's correct there, but opening the same URL
   from an actual external browser needs the instance's PUBLIC IPv4 address
   instead - the private IP just times out from outside the VPC, which
   looks identical to a missing firewall rule or a TLS problem but is
   neither. Documented explicitly in the guide (Step 8's note) since the
   symptom is genuinely misleading.

8. Multi-node join VERIFIED end-to-end for the first time on two separate
   real EC2 instances (same AWS account/VPC/region - a different-account
   attempt was tried first and correctly fails: 172.31.x private IPs only
   route within one VPC, and that isn't fixable by any security-group rule,
   only by using instances in the same VPC or setting up peering, which
   isn't covered). `./scripts/node-join.sh user@<worker-ip>` (remote mode,
   dispatched over SSH from the control-plane) succeeded once two things
   were both true:
     - the control-plane instance itself (not the operator's laptop) needs
       the worker's SSH private key, since it's the one dispatching the
       join - easy to miss when the key only exists on the operator's own
       machine; and
     - security groups need rules in BOTH directions. The worker's own SG
       needs to accept 6443/10250/51820 FROM the control-plane (documented
       already), but the CONTROL-PLANE's SG ALSO needs new inbound rules
       accepting 6443/10250/51820 FROM the worker - missing this manifests
       as an indefinite hang on the worker's `k3s-agent` logs
       ("failed to get CA certs: ... context deadline exceeded"), which
       looks like an SSH/key problem but is actually the reverse-direction
       firewall rule nobody thought to add. `kubectl get nodes -o wide`
       showed both nodes Ready once both issues were fixed. As designed,
       the joined node is agent-only - it adds capacity, never control-
       plane redundancy (single k3s SERVER, no embedded-etcd HA); this was
       confirmed, not changed, in this session.
       Documented in INSTALL_GUIDE.md's new "Adding a worker node" section.
