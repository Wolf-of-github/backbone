- Diagram
  - auth
    - Passport.js + JWT
  - api-gateway
    - Kong
      - Single entry point for all services
      - Load balancing (automatic)
      - Request/response transformation (add defaults, extract JWT data)
      - Rate limiting, authentication plugins
      - Routing: / → frontend, /api/* → backend services
  - frontend
    - React app containerized with NGINX
      - Multi-stage Docker build (Node.js build + NGINX serve)
      - Served from NGINX container
      - Deployed in k3s cluster
      - Kong routes root path to frontend service
  - database
    - MongoDB (primary NoSQL)
  - job-queue
    - Redis + BullMQ
      - Redis for storage
      - BullMQ for queue management
      - Features: Auto-retry, job status tracking, priority queues
      - Workers pull jobs from queue for processing big tasks
  - logging-monitoring
    - PLG Stack (Prometheus + Loki + Grafana)
      - Prometheus: Metrics collection (CPU, memory, request rates, errors)
      - Loki: Centralized logging from all services
      - Grafana: Unified dashboard for logs and metrics
      - Auto-discovery of k3s services
      - Alerting for critical issues
  - secrets-management
    - k3s Native Secrets
      - Built-in k3s secrets (no extra pods)
      - Store API keys, DB passwords, JWT secrets
      - Inject as environment variables into pods
      - Upgrade to Sealed Secrets for production if needed
  - ssl-tls
    - cert-manager + Let's Encrypt
      - cert-manager pod manages SSL certificates
      - Let's Encrypt provides free SSL certificates
      - Automatic certificate issuance and renewal (every 90 days)
      - Integrates with Kong for HTTPS
      - Zero maintenance after setup
  - ci-cd
    - Gitea + Drone CI (self-hosted)
      - Gitea: Self-hosted Git repository
      - Drone CI: Lightweight CI/CD pipeline runner
      - Docker Registry: Store built images (Gitea built-in or separate)
      - Pipeline: Push to Git → Run tests → Build Docker image → Deploy to k3s
      - k3s rolling updates (zero downtime deployment)
      - Auto-rollback on failed health checks
      - Database migration strategy with up/down scripts
      - Notifications on success/failure
  - backup-disaster-recovery
    - MongoDB Backups
      - k3s CronJob runs mongodump every 7 days
      - Stored in persistent volumes
      - Optional: External storage (self-hosted MinIO)
    - Redis Persistence
      - RDB: Snapshots every 15 minutes (fast recovery)
      - AOF: Append-only log for every write (minimal data loss)
      - Auto-compaction when AOF grows too large
      - Stored in persistent volumes
    - Server Failure Handling
      - k3s multi-node cluster (main + worker nodes)
      - Automatic pod rescheduling if node fails
      - Persistent volumes for data survival
      - Optional: MongoDB replica set for high availability
  - deployment
    - k3s (lightweight Kubernetes)
      - Auto-scaling for big tasks
      - Multi-server orchestration
      - Worker nodes for task processing
      - Self-hosted, zero external dependencies
  - maintenance
    - Static maintenance page (NGINX container)
      - Always-running deployment, minimal resources
      - Serves single static HTML, HTTP 503 + Retry-After header
      - Activated/deactivated by toggling Kong routing (not by start/stop)
      - `maintenance on|off` CLI wraps Kong Admin API
      - Deactivation also exposed via admin-auth endpoint (POST /internal/maintenance/off)
        - Callable from CLI or a login-gated control on the maintenance page
      - Bypass list: maintenance-off endpoint, health checks, /metrics
      - State persisted in ConfigMap so it survives Kong/pod restarts
      - Optional: pause BullMQ queues while in maintenance
  - security
    - Baseline application security guidelines (enforced in code review + CI)
      - Injection: no shell string interpolation
        - Use execFile/spawn with arg arrays, not exec() / child_process.exec
        - Python: subprocess.run([...]) without shell=True, never os.system()
        - Parameterized DB queries only, never string-built MongoDB queries
      - Code execution: no eval(), no new Function() on dynamic strings
      - XSS: no raw innerHTML / outerHTML / insertAdjacentHTML / document.write
        - React: avoid dangerouslySetInnerHTML; sanitize with DOMPurify if unavoidable
        - Escape/encode all user content on output; set a strict Content-Security-Policy
      - Unsafe deserialization: no pickle/marshal/yaml.load on untrusted input
        - Use JSON or schema-validated parsers (pydantic, zod); yaml.safe_load only
      - XXE: use a hardened XML parser (defusedxml), external entities disabled
      - Secrets: never hardcode keys/passwords/tokens; load from k3s secrets
        - Secret scanning in CI to block commits containing credentials
      - Crypto: AES-GCM (or AES-CBC + HMAC), never ECB; use createCipheriv with IV
        - Bcrypt/argon2 for passwords; never MD5/SHA1 for auth
      - TLS: never disable certificate verification (no rejectUnauthorized:false,
        verify=False, InsecureSkipVerify)
      - Access control: authenticate every request at the gateway; enforce object-level
        authorization in services (prevent IDOR); deny by default
      - SSRF: validate/allowlist outbound URLs from user input; block internal IP ranges
      - Path traversal: normalize paths, confine to an allowed base directory
      - CI/CD: no untrusted input in shell steps or checkout refs; pin action versions
      - Dependencies: lockfiles, npm audit / CVE scan in pipeline, patch critical/high
      - Enforcement: security-guidance plugin (edit-time pattern warnings, LLM diff
        review, agentic commit review) gates every change before merge
  - horizontal-scale
    - The point of backbone: add machines, get capacity - no per-service rewiring. Linux only.
    - Shape: a real k3s SERVER (control plane, embedded etcd) on one Linux host; every other machine
      (EC2, spare box, another cloud) joins as a k3s AGENT with `scripts/node-join.sh`.
      Any laptop drives the cluster by pointing kubectl at ./kubeconfig - nothing installed on the laptop.
    - Why not "k3s in Docker" (k3d/kind) as the default: those run on one Docker daemon = one machine.
      They give orchestration within that machine's RAM/CPU ceiling, never additional hardware. Offloading
      heavy work needs another machine's kernel, which means real k3s on each. (k3d stays useful only as a
      throwaway local dev cluster - not part of Phase 0.)
    - A joined machine installs ONLY the k3s agent (~100 MB, its own containerd). No Docker, no kubectl.
      One command: `curl ... | K3S_URL=https://<server>:6443 K3S_TOKEN=<tok> sh -` (node-join.sh wraps it).
    - Location transparency: a pod on the EC2 node and a pod on the main box talk via the same
      `svc.namespace.svc.cluster.local` DNS. The flannel overlay carries pod-to-pod across machines.
      You never wire IPs between services.
    - Scaling a service = raise `replicas` / HPA `maxReplicas`; the scheduler spreads pods across all
      nodes. Out of room -> join another machine. No reconfiguration.
    - Node-to-node networking (the one real cost). Open BETWEEN nodes only
      (e.g. one AWS security group referencing itself):
        6443/tcp   Kubernetes API      (agents -> server)
        10250/tcp  kubelet             (all <-> all)
        51820/udp  flannel WireGuard   (all <-> all)   [WIREGUARD=true, default]
        8472/udp   flannel VXLAN       (all <-> all)   [WIREGUARD=false, trusted network only]
      Cross-network (home/office <-> AWS VPC): WIREGUARD=true (encrypts the overlay) + NODE_EXTERNAL_IP
      set to each node's routable IP. Same-VPC: plain VXLAN is fine.
    - Failure: an agent dying -> its pods reschedule onto the others. The server is still a single
      point of failure until Phase 6 (embedded-etcd HA: 3 servers).
    - External services that will NEVER run in-cluster (managed RDS, a GPU box you won't put k3s on):
      represent them as a selector-less Service + EndpointSlice, or ExternalName. Callers use a normal
      Service DNS name; the target lives outside. This is the exception, not the scaling mechanism.

    - Runtime decision: LINUX ONLY. `make cluster` installs a real k3s SERVER (control plane, embedded

      Any laptop drives the cluster by pointing kubectl at ./kubeconfig - nothing installed on the laptop.
      - Prereqs on the server: Linux + `curl` + `sudo` + `kubectl`.
        Prereqs on a joining worker: Linux + `curl` + `sudo` ONLY (no Docker, no kubectl).
      - `scripts/cluster-up.sh` installs k3s server with `--cluster-init`, `--disable=traefik`,
        `--flannel-backend=wireguard-native` when WIREGUARD=true, `--tls-san`/`--node-external-ip`/role
        label from .env. Caches the join token to `.secrets/cluster-join.env` (gitignored).
      - No in-cluster registry in Phase 0 - workers pull from public registries until Phase 5 stands up
        the real one (authenticated, behind Kong + TLS).
      - Why not k3d/kind ("k3s in Docker") even for a single machine: they run on one Docker daemon =
        one machine's RAM/CPU. They cannot pool other machines' hardware, which is the whole point of
        backbone. k3d remains only a throwaway local dev cluster - not part of Phase 0.
      - DROPPED from earlier drafts: k3s-config.yaml, kubeconfig.example, registry-secret.sh,
        bootstrap-registry.sh, registries.yaml(.example), k8s/platform/registry/*, config/k3d-cluster.yaml,
        and the MULTI_NODE switch. The k3s-server install is now the only path in cluster-up.sh.

    - Guiding rules
      - Bottom-up by depends_on: never create a file before the files it depends on are in place.
      - Two passes per file: (1) instantiate with a header comment (purpose + depends_on, body `# STUB`);
        (2) implement - real content, remove the STUB marker.
      - Nothing is "done" until `make verify` (verify-phase0.sh) prints "PHASE 0 OK" and `make` exits 0
        on a freshly installed server.
      - Security from commit #1: `.gitignore` first; `.env`, `./kubeconfig`, `.secrets/` (join token),
        and any future cert material always ignored; `set -euo pipefail` in every script; never echo
        secret values.

      - Instantiate headered stubs:

      - Verify: `grep` that .env / kubeconfig / .secrets are ignored; `bash -n` on all scripts.

    - Step 2 - Cluster bring-up (scripts/cluster-up.sh + node-join.sh)
      - lib.sh: REPO_ROOT, KUBECONFIG default = ./kubeconfig, load_env, require_vars, need, log/ok/die.
      - cluster-up.sh: `set -euo pipefail`; source lib; load_env; require Linux + curl + sudo;
        require_vars K3S_VERSION CLUSTER_NAME K3S_SERVER_ADDR; normalise K3S_VERSION (-k3s -> +k3s);
        `curl -sfL https://get.k3s.io | INSTALL_K3S_EXEC="server --cluster-init --tls-san=<addr>
        --disable=traefik [--flannel-backend=wireguard-native] [--node-external-ip=<ip>]
        --node-label=backbone.dev/role=<role> --write-kubeconfig-mode=0644" sh -`;
        write ./kubeconfig (server URL rewritten to K3S_SERVER_ADDR, mode 0600); cache
        .secrets/cluster-join.env (K3S_URL + node-token, umask 077); `kubectl wait` node Ready;
        print both node-join invocations + the node-to-node port list. Idempotent (re-runs reconcile).
      - node-join.sh: join a machine as a k3s AGENT.
        Local mode (on the worker): K3S_URL + K3S_TOKEN from env or .secrets/cluster-join.env, then
        `curl get.k3s.io | K3S_URL/K3S_TOKEN INSTALL_K3S_EXEC="agent
        --node-label=backbone.dev/role=worker [--node-external-ip=...]" sh -`; prints required ports.
        Remote mode (`node-join.sh user@host` on the server): reads cached creds, `ssh`es this script
        to the target with them and runs it there.
      - cluster-down.sh: run `/usr/local/bin/k3s-uninstall.sh` on this host; remind that each worker
        runs `/usr/local/bin/k3s-agent-uninstall.sh`; rm ./kubeconfig + .secrets/cluster-join.env.
      - Verify: server node Ready; `kubectl get sc` shows local-path; `kubectl get nodes -L
        backbone.dev/role`; after a join, the new node shows Ready within ~30s.

    - Step 3 - Cluster base objects (k8s/base/*.yaml)
      - storageclass.yaml: desired end state for the default `local-path` SC (is-default-class annotation,
        reclaimPolicy Delete, WaitForFirstConsumer). Applied in practice via `kubectl patch` in `make base`
        (the shipped SC has immutable fields); this file is the spec + dry-run target.
      - namespaces.yaml: Namespace objects platform, data, app (observability, ci commented for Phase 5).
      - Verify: `kubectl get ns` shows the three; `kubectl get sc` shows local-path marked (default).

    - Step 4 - Secrets convention (scripts/create-secrets.sh)
      - Phase 0 creates NONE. create-secrets.sh is the stable entrypoint: `set -euo pipefail`, load_env,
        assert namespaces exist, print "no secrets to create", exit 0. Later `<phase>-secrets.sh` plug in
        here using the idempotent `kubectl create secret ... --dry-run=client -o yaml | kubectl apply -f -`
        pattern (documented inline).
      - Verify: `make secrets` exits 0 on a cluster with the namespaces; fails clearly without them.

    - Step 5 - Makefile wiring
      - Targets (.PHONY; `KUBECONFIG ?= ./kubeconfig` exported at top):
        `make phase0`                     -> cluster base secrets verify
        `make cluster`                    -> scripts/cluster-up.sh   (install the k3s server)
        `make base`                       -> kubectl apply namespaces.yaml + patch local-path default
        `make secrets`                    -> scripts/create-secrets.sh
        `make verify`                     -> scripts/verify-phase0.sh
        `make node-join TARGET=user@host` -> scripts/node-join.sh (SSH join a worker)
        `make down`                       -> scripts/cluster-down.sh (uninstall the k3s server)
        `make lint`                       -> shellcheck scripts + `kubectl apply --dry-run=server -f k8s/base/`
      - Every target except `cluster`/`down`/`node-join` fails fast if ./kubeconfig is missing.

    - Step 6 - Verification script (scripts/verify-phase0.sh) - the 100% gate
      - `set -euo pipefail`; source lib; load_env; KUBECONFIG=./kubeconfig.
      - [1] `kubectl wait` node(s) Ready.
      - [2] exactly one default StorageClass and it is `local-path`.
      - [3] namespaces platform/data/app exist AND each has its `default` ServiceAccount
            (poll up to ~30s - the token controller creates it a beat after the namespace).
      - [4] apply a 1Gi PVC + a busybox consumer pod in `data` (local-path is WaitForFirstConsumer),
            `kubectl wait` pvc Bound, then clean up.
      - [5] one pinned busybox pod per node (nodeName=<n>) all reach Succeeded - proves every node can
            pull and run an image. (The shared authenticated in-cluster registry lands in Phase 5.)
      - Exit non-zero with a clear message on the first failed assertion; print "PHASE 0 OK" on success.

    - Step 7 - Clean-machine dry run
      - On a fresh Linux server VM: `cp .env.example .env`, set K3S_SERVER_ADDR (+ NODE_EXTERNAL_IP if
        workers are on another network), `make phase0` -> "PHASE 0 OK".
      - On a second Linux VM: `make node-join TARGET=user@<server-or-run-on-worker>` (or the printed
        one-liner). Confirm `kubectl get nodes` shows both Ready and `make verify` passes with 2 nodes.
      - Tag `phase-0-complete` once `make phase0` is green from scratch and >=1 worker has joined and
        passed verify.

    - Definition of done (Phase 0)
      - Every file in "Files (Phase 0 - Substrate)" exists with real content (no STUB markers).
      - On a Linux server: `make phase0` -> "PHASE 0 OK" and `make` exits 0; `make down` uninstalls it.
      - A second Linux box joins with one command, appears Ready, and `make verify` passes multi-node.
      - No .env, ./kubeconfig, or secret material (incl. the join token) committed; scripts pass
        `bash -n` (shellcheck where available); k8s/base passes `kubectl apply --dry-run=server`.
      - README covers the flow and lets a new person reproduce it unaided.

    # --- SERVER host (control plane) ---
    $ sudo apt-get update && sudo apt-get install -y curl        # + sudo (already present)
    $ sudo snap install kubectl --classic                        # or per distro / cloud

    # --- each WORKER host ---
    $ sudo apt-get update && sudo apt-get install -y curl        # curl + sudo are the ONLY worker prereqs

    #     make secrets  -> ./scripts/create-secrets.sh   (no-op in Phase 0)

    $ sudo systemctl stop k3s-agent  # same, on a worker

    #   on EACH worker:
    $ sudo /usr/local/bin/k3s-agent-uninstall.sh

  == 6. Checks / troubleshooting ==
    $ make lint                                            # shellcheck + kubectl --dry-run=server -f k8s/base/
    $ for f in scripts/*.sh; do bash -n "$f"; done         # script syntax
    $ kubectl get pods -A                                  # everything Running/Completed
    $ kubectl -n data get pvc                              # PVCs Bound
    #   worker stuck NotReady?   check the 3 ports above; on the worker: sudo systemctl status k3s-agent; journalctl -u k3s-agent -f
    #   need the join token?     on the server: sudo cat /var/lib/rancher/k3s/server/node-token
    #   server won't start?      journalctl -u k3s -f ; check K3S_SERVER_ADDR resolves and :6443 is free

- Build Order (dependency-ordered; each layer stands on a working one below it)
  - Core chain: k3s → container registry → Kong → one real service → MongoDB/Redis → auth → CI/CD → observability → TLS → backups → maintenance
  - Phase 0 - Substrate
    - Cluster: k3s SERVER on a Linux host (`make cluster`); each extra Linux machine joins with
      `scripts/node-join.sh` (see Diagram > horizontal-scale). kubectl working, default StorageClass
      (local-path), PVCs bind.
    - Container registry: none in Phase 0 - workers pull from public registries. The real authenticated
      in-cluster registry is deferred to Phase 5 (behind Kong + TLS).
    - Namespace split + secrets convention (no K8s secrets in Phase 0; k3s join token cached under .secrets/).
  - Phase 1 - Data layer
    - MongoDB (StatefulSet + PVC, single instance, no replica set yet)
    - Redis (PVC, RDB enabled) - needed by BullMQ and Kong rate-limiting
  - Phase 2 - Edge
    - Kong (declarative/DB-less mode; routes / and /api/*) - integration point for auth, TLS, rate limiting, maintenance
    - One trivial backend service (/api/ping) - end-to-end smoke test for every later change
    - Frontend (React + NGINX image; Kong routes / to it)
  - Phase 3 - Identity
    - Auth service (Passport.js + JWT) issues tokens; Kong JWT plugin validates + injects claims
    - Test IDOR / deny-by-default here
  - Phase 4 - Async work
    - BullMQ workers (separate Deployment, pulls from Redis) - after real jobs exist
  - Phase 5 - Operate
    - CI/CD (Gitea + Drone) - replaces manual push/apply; deliberately after manual path proven
    - Observability (PLG stack) - no hard dependents; can slot earlier for bring-up visibility
    - cert-manager + Let's Encrypt - needs real domain + Kong terminating traffic
  - Phase 6 - Resilience & lifecycle
    - Backup/DR (mongodump CronJob, Redis AOF, then replica set + multi-node k3s)
    - Maintenance page (static 503 + maintenance CLI + ConfigMap state) - needs Kong Admin API + CI/CD
  - Cross-cutting (from commit #1, never "done")
    - Security guidelines: enable security-guidance plugin + CI checks (secret scanning,
      no exec(), parameterized queries) as soon as a repo exists
  - Minimum viable spine: k3s → registry → MongoDB + Redis → Kong → one placeholder service

- Phase 0 - what is accomplished
  The substrate everything else runs on. `make phase0` on a Linux host delivers:
  1. A k3s cluster - k3s server installed on the host (embedded etcd; Traefik disabled, Kong comes later).
  2. Horizontal scale built in - any other Linux machine joins as a worker with one command
     (`make node-join TARGET=user@ip`) over a WireGuard-encrypted overlay. The scheduler spreads pods
     across all nodes; services reach each other by DNS regardless of which machine they land on.
  3. Working storage - `local-path` set as the default StorageClass, so PVCs bind with no annotation.
  4. Namespace layout - `platform` / `data` / `app`.
  5. A secrets convention - no secrets yet, but `create-secrets.sh` is the stable entrypoint later
     phases plug into; the k3s join token is cached to `.secrets/` (gitignored).
  6. An acceptance gate - `make verify` asserts nodes Ready, default SC correct, namespaces present,
     a PVC binds, and every node can pull an image -> prints "PHASE 0 OK".
  Plus repo scaffolding: Makefile, .env.example, .gitignore, README.md, architecture.txt.
  NOT included (deferred by design): the authenticated image registry, Kong, databases, TLS - Phases 1-5.
  Status: implemented; scripts pass `bash -n`. End-to-end run (server + a joined worker) is Step 7,
  pending real Linux hosts, before tagging `phase-0-complete`.

- Files (Phase 6 - Resilience & lifecycle)
  Format: file_name | file_path | description | depends_on[]
  Two tracks: Backup/DR (data + platform ns) and Maintenance (platform ns).
  Backup/DR builds on Phase 1 data + optional Phase 5 MinIO; Maintenance builds on Kong Admin API (Phase 2) and reuses CI/notify (Phase 5).

  == Track A: Backup / Disaster Recovery ==

      | depends_on: [k8s/base/namespaces.yaml, scripts/create-secrets.sh]
    - minio-statefulset.yaml | /k8s/data/minio/statefulset.yaml
